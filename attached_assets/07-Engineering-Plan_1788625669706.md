# TakeOnTime — Engineering Plan

**Version:** 1.0
**Build cadence:** One day at a time, per-app, per-module — never skip a layer (DB → RLS → FlutterFlow UI → backend wiring → testing) within a day's scope.
**Sequencing:** **Vendor app fully first → Customer app → Admin panel.**

## 2. Feature → Story Breakdown (Representative — Vendor App)

### E1 — Foundation
- **Story:** As a new vendor, I can sign up and land in a `pending_approval` state.
  - Task: Create `users` table + `on auth.users insert` trigger.
  - Task: Build Auth pages (login/signup) in FlutterFlow.
  - Task: Build router logic — `pending_approval` / `account_issue` / `MainNavPage` stub pages, dispatched from `vendors.is_approved`/`approval_note`.
  - **Acceptance criteria:** A freshly signed-up vendor account, with no `vendors` row approved, is routed to `PendingApprovalPage` and cannot reach `MainNavPage`.

### E2 — Store Operations (already delivered — recorded for traceability)
- **Story:** As a vendor, I can toggle whether I'm accepting orders. — **Done.**
- **Story:** As a vendor, I can pause orders temporarily without going fully closed. — **Done.**
  - Acceptance criteria (met): status badge shows On Break (red) > Closed (grey) > Open (green) precedence; break countdown is display-only, derived from `break_until`.
- **Story:** As a vendor, I have quick shortcuts to common actions from the Store tab. — **Done** (2 wired cards: Today's Orders, Low Stock stub; 2 placeholder slots).

### E3 — Menu Management (Categories delivered; Items list delivered; Item Form pending)
- **Story:** Categories CRUD — **Done** (Day 3, Page 1).
- **Story:** Items list per category with search/filter — **Done** (spec delivered; build pending confirmation).
- **Story (next):** Item Form Page (create/edit) — name, description, price, image upload, sold-out toggle.
  - Task: `menu_items` table + RLS (per `06-API-Data-Design.md §2.4`).
  - Task: Supabase Storage bucket `item-images` + policies.
  - Task: FlutterFlow form page with image picker → upload → `image_url` write.
  - Task: Wire "Add Item" / "Edit Item" navigation from Items List Page (already spec'd with `itemId`/`categoryId` params).
  - **Acceptance criteria:** Creating an item with an image results in a working public `image_url`; editing preserves `category_id`; sold-out toggle immediately reflects on the Items List status chip.

### E4 — Order Management
- **Story:** As a vendor, I see new orders appear live without refreshing.
  - Task: `orders`/`order_items` tables + RLS (client select-only).
  - Task: Realtime subscription wired into Orders tab.
  - Task: Accept/Reject actions call `update-order-status` Edge Function.
  - **Acceptance criteria:** A test order created via Edge Function appears in the Vendor app's Orders tab within 3 seconds without manual refresh.

### E5 — Vendor Notifications
- Task: FCM setup (Firebase project, FlutterFlow FCM integration, device token capture into `users`/a `device_tokens` table).
- Task: `send-fcm-notification` Edge Function, triggered on new order + status-relevant events.
- **Acceptance criteria:** New order → vendor receives a push within a few seconds of the DB row being created, app backgrounded or foregrounded.

*(Customer app — E6–E10 — and Admin panel — E11–E13 — follow the same story/task/acceptance-criteria pattern; not fully expanded here to avoid duplicating `01-PRD.md §6`. Expand each epic into stories at the start of its build phase, i.e., once Vendor app epics E1–E5 are fully closed.)*

## 3. Dependencies

- E3 (Menu Management) depends on E1 (vendor must exist/be identifiable via `currentVendorId`).
- E4 (Orders) depends on E3 (order_items reference real menu_items) and on Customer app's E9 existing enough to generate test orders — cross-app dependency, mitigate by seeding test orders directly via SQL/Edge Function during Vendor-app-only development.
- E9 (Checkout & Payments) depends on E7/E8 (discovery + cart) and requires Razorpay test-mode credentials configured before any Edge Function work begins.
- E12 (Admin approval) depends on E1's `is_approved`/`approval_note` fields already existing in `vendors` — schema for this must be created during E1, not deferred to the Admin build phase, since Vendor app's routing logic (`PendingApprovalPage`) reads it from day one.

## 4. Milestones

| Milestone | Contents | Definition of Done |
|---|---|---|
| M1 — Vendor Core Live | E1–E3 complete | A vendor can sign up, get approved (manually via SQL for now), and build a full menu. |

## 5. Development Sequencing Rules (project-specific)

1. **Vendor app fully, then Customer app, then Admin panel** — no epic from a later app starts before all epics in the earlier app are functionally complete (per explicit project instruction).
2. Within an app, build **one page at a time**, in the structure: DB/SQL → RLS → RLS test → FlutterFlow schema sync → UI → wiring → testing → deliverables checklist — before moving to the next page.
3. Never proceed to the next day/page until the current one's testing checklist is fully checked off.
4. Any stub referenced by routing logic (e.g., `PendingApprovalPage`, `AccountIssuePage`) must be built as a real page — even minimally — before being left as a dangling "TODO," to avoid broken navigation targets accumulating.
