## 2. Frontend Architecture

- **Three independent FlutterFlow projects**, each compiled to its own app/deployable — deliberately **not** one app with role-based routing, so that:
  - Vendor and Customer apps can be released/updated independently.
  - Store bundle size stays small (no dead code for the "other" role).
  - Admin panel can be web-only without mobile packaging overhead.
- Each app authenticates against the **same** Supabase Auth instance and shares the **`users`** table, so a single email could theoretically exist as both a customer and (separately) a vendor owner, distinguished by which app-specific table (`vendors`) references their `users.id`.
- Client apps talk to Postgres **only** through the Supabase client SDK using the **anon key + the user's JWT** — RLS is the only authorization boundary for direct table access. Anything that needs elevated privilege (service role) goes through an Edge Function instead.
- FlutterFlow "App State" is used only for session-scoped convenience values (e.g., cached `currentVendorId`) that are always re-derived from a DB query at page load, per the state-derivation rule in `03-TRD.md` — App State is a cache, never a source of truth.

## 3. Backend Architecture

### 3.1 Database (Postgres via Supabase)
- Every table has RLS **enabled by default** the moment it's created; policies are written before any client code touches the table.
- Ownership chain pattern used throughout: `auth.uid() → users.id → vendors.owner_id → vendors.id → (menu_categories/menu_items/orders).vendor_id`. All vendor-scoped RLS policies resolve through this chain via a subquery, e.g.:
  ```sql
  vendor_id in (select id from public.vendors where owner_id = auth.uid())
  ```
- A shared `set_updated_at()` trigger function is reused across every table with an `updated_at` column (already established convention from `menu_categories`).

### 3.2 Edge Functions (Deno/TypeScript)
Used specifically where logic must not be trusted to the client or bypassed via direct table RLS:

| Function | Responsibility |
|---|---|
| `create-order` | Validates cart contents against live vendor/menu state, creates `orders` + `order_items` in one transaction, initiates a Razorpay order. |
| `razorpay-webhook` | Verifies Razorpay signature, marks payment captured, transitions order out of `pending_payment`. Idempotent on `razorpay_payment_id`. |
| `approve-vendor` | Admin-only (checked via `users.role = 'admin'`); flips `vendors.is_approved`, triggers vendor notification. |
| `send-fcm-notification` | Called by DB triggers/other functions on relevant state changes; wraps FCM Admin SDK/HTTP v1 API call. |
| `update-order-status` | Enforces the legal state machine for order status transitions (see `06-API-Data-Design.md`); rejects illegal transitions server-side even if attempted via a well-formed request. |

### 3.3 Realtime
- Enabled on `orders` (row-level, filtered client-side to the relevant `vendor_id` or `customer_id`) so both Vendor and Customer apps get live updates without polling.
- Optionally enabled on `vendors` (`accepting_orders`, `break_until`) so the Customer app's discovery list updates live without a manual refresh.

### 3.4 Storage
- Buckets: `vendor-logos` (public read), `item-images` (public read), both with **write** policies restricted to the owning vendor (`owner_id = auth.uid()` resolved the same way as table RLS).
- Images referenced in Postgres by their public Storage URL, not stored as binary in the DB.

### 3.5 Cron (pg_cron)
- `expire-temporary-break`: runs every minute; for any vendor where `break_until <= now()`, no explicit DB write is strictly required since status is derived from `break_until` at read time — but a cleanup job may null out stale `break_until` values for hygiene and to keep the "On Break" Realtime signal accurate for subscribers without them re-evaluating time client-side.

## 4. Authentication & Authorization

- **AuthN:** Supabase Auth (email/password to start; phone OTP as an extension point) — identical mechanism across all three apps, since they share one Supabase project.
- **AuthZ layers (defense in depth):**
  1. RLS policies on every table (primary boundary for direct DB access).
  2. Edge Function-level role checks for admin-only or money-moving operations (belt-and-suspenders — RLS could theoretically be misconfigured, so sensitive Edge Functions re-verify role/ownership explicitly rather than trusting the caller's claimed identity blindly).
  3. Storage bucket policies mirroring table RLS for uploaded assets.
- No custom JWT issuance — Supabase-issued JWTs are used as-is; `role` distinctions (customer/vendor/admin) live in the `users` table, **not** encoded as a Postgres role or custom JWT claim, to keep the auth model simple for MVP.

## 5. Caching

- No dedicated cache layer (e.g., Redis) at MVP scale — Postgres + Supabase's built-in connection pooling (PgBouncer) is sufficient for expected load.
- FlutterFlow client-side query caching is used only for non-critical, slow-changing data (e.g., category taxonomy for admin config); anything status-sensitive (store status, order status) always re-fetches or subscribes live.

## 6. Queues

- No external queue system for MVP. Order/payment reliability is handled via Razorpay's own webhook retry behavior + idempotent Edge Function handlers, which is sufficient at MVP order volume. Revisit (e.g., Supabase Queues or a dedicated job runner) if webhook processing needs to be decoupled from request/response latency at higher scale.

## 7. External Services

| Service | Purpose | Failure mode handling |
|---|---|---|
| Razorpay | Payment capture, prepaid checkout | Order stays `pending_payment`; customer sees retry option; no order is "confirmed" without a verified webhook. |
| FCM | Push notifications | Best-effort; DB state (Realtime) is the source of truth, push is a convenience layer — a missed push must never leave the app showing stale state once reopened. |
| Supabase Storage | Image hosting | Client shows a placeholder image if the URL 404s; upload failures block save with a clear error, never silently drop the image reference. |

## 9. Architecture Decision Records (ADRs)

### ADR-001: Three separate apps instead of one role-based app
**Decision:** Build independent Vendor, Customer, and Admin(web) FlutterFlow apps sharing one Supabase backend, rather than a single app with role-based routing.
**Rationale:** Smaller, faster, more focused apps per audience; independent release cadence; avoids leaking vendor-only UI/logic into the customer bundle; matches how the project was actually scoped and built.
**Status:** Accepted (established in Day 1 setup).

### ADR-002: `users` table instead of `profiles`
**Decision:** Name the shared identity table `users`, not the common Supabase-community convention of `profiles`.
**Rationale:** Explicit project requirement; keeps naming intuitive for a team not deeply steeped in Supabase conventions.
**Status:** Accepted.

### ADR-003: Prepaid-only, no COD at MVP
**Decision:** All orders must be paid via Razorpay before confirmation; no cash-on-delivery/pickup flow exists in the schema or state machine.
**Rationale:** Simplifies reconciliation, reduces no-show risk, matches founder's current business model choice.
**Status:** Accepted; explicitly revisitable post-MVP (would require schema + state machine additions, not a rewrite).

### ADR-004: Modal returns data, parent writes to DB
**Decision:** Input-collecting modals/dialogs (e.g., Temporary Break duration picker) never write to the database themselves — they return the collected value to the calling page, which performs the write.
**Rationale:** Centralizes DB write logic per page, makes testing/debugging simpler, avoids duplicate write paths for the same underlying state.
**Status:** Accepted (established during Store tab build, Day 2).

### ADR-005: Reusable components stay presentation-only where FlutterFlow can't pass action params
**Decision:** Components like `QuickActionCard` hold no navigation/action logic internally; the wrapping widget at each call site owns the `onTap` behavior.
**Rationale:** FlutterFlow version limitations around passing actions as component parameters; keeps the component genuinely reusable across different action targets.
**Status:** Accepted; revisit if/when FlutterFlow's Widget Actions-as-params support is confirmed stable across the team's version.
