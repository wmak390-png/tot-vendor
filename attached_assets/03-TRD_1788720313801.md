# TakeOnTime — Technical Requirements Document (TRD)

**Version:** 1.0
**Companion to:** `01-PRD.md`, `05-Architecture.md`, `06-API-Data-Design.md`

---

## 1. Functional Technical Requirements

| ID | Requirement |
|---|---|
| FTR-1 | Three independent FlutterFlow apps (Vendor mobile, Customer mobile, Admin web) connect to one shared Supabase project. |
| FTR-2 | Shared identity table is named **`users`** (not `profiles`) — every Supabase Auth user gets exactly one row, created via a DB trigger on `auth.users` insert. |
| FTR-3 | Vendor business data lives in `vendors`, keyed by `owner_id → users.id` (1 owner : 1 vendor for MVP; extensible to staff-per-vendor later). |
| FTR-4 | Menu structure is two-level: `menu_categories → menu_items`, both scoped to `vendor_id`, both RLS-protected via `vendor_id in (select id from vendors where owner_id = auth.uid())`. |
| FTR-5 | Orders must never be created client-side as "paid" — payment confirmation must be verified server-side (Edge Function + Razorpay webhook signature check) before order status can leave `pending_payment`. |
| FTR-6 | Order status transitions must be enforced server-side (via Edge Function or Postgres function + trigger) to prevent illegal transitions (e.g., `ready → confirmed`). |
| FTR-7 | Store state (`accepting_orders`, `break_until`) must be authoritative in the DB; all UI reads derive state from the DB on every refresh — no client-cached "is open" flag is treated as source of truth. |
| FTR-8 | Order status changes must be pushed to the customer app via Supabase Realtime (Postgres changes on `orders`) and mirrored as an FCM push via Edge Function trigger. |
| FTR-9 | COD is explicitly unsupported — no `payment_method = 'cod'` value exists in the schema for MVP. |
| FTR-10 | Vendor onboarding requires admin approval (`vendors.is_approved`) before the vendor is discoverable/orderable in the Customer app. |

## 2. Non-Functional Requirements

### 2.1 Performance
- List queries (categories, items, orders) must be indexed on their filter column (`vendor_id`, `category_id`, `status`) — no full table scans on RLS-protected tables at MVP scale (<10k rows/table).
- Realtime subscription payloads limited to the changed row only (no broad table-wide broadcast).
- Image assets (item photos, business logos) served via Supabase Storage public/CDN URLs, not stored as base64 in Postgres.

### 2.2 Scalability
- Schema designed so a vendor can later have multiple staff/devices (extend `users ↔ vendors` to a join table `vendor_staff` without breaking `owner_id` semantics).
- Edge Functions are stateless — horizontal scaling is Supabase-managed, not a concern for app code.
- Partitioning/archival of `orders` deferred until volume requires it (>~1M rows) — not an MVP concern, but no design decision should block it (e.g., always include `created_at` for future range partitioning).

### 2.3 Availability
- Target 99.5% uptime for MVP, inherited from Supabase's SLA tier; no custom failover infra required at this stage.
- Vendor app must degrade gracefully (cached last-known store status + explicit "offline" banner) if Supabase is unreachable — never show a false "Open" state on connectivity failure.

### 2.4 Compatibility
- Vendor & Customer apps: iOS 13+ / Android 8+ (FlutterFlow-generated Flutter app baseline).
- Admin web panel: evergreen Chrome/Edge/Safari/Firefox (last 2 versions).

### 2.5 Security Requirements
- All tables containing vendor- or user-scoped data have RLS **enabled and enforced**, no table is left with RLS disabled "temporarily."
- Service-role key never shipped to any client app; only used inside Edge Functions.
- Razorpay webhook endpoint verifies the `X-Razorpay-Signature` header against the webhook secret before trusting payload contents.
- All Edge Function inputs are validated (type + required fields) before touching the DB; malformed input returns `400`, never a raw stack trace.
- Admin panel access gated by a `role = 'admin'` check in `users`, enforced both by RLS on admin-only tables/views **and** by an Edge Function check for admin-only mutations (defense in depth, not RLS alone).

### 2.6 Reliability
- Any Edge Function that mutates money/order state must be idempotent (safe to retry) — keyed by a client-supplied `idempotency_key` or the Razorpay `payment_id`/`order_id` pair, to survive webhook retries or client double-taps.
- Database writes affecting multiple tables in one logical operation (e.g., "create order + create order_items + decrement... [future stock]") are wrapped in a single transaction inside the Edge Function/Postgres function, not sequential client-side calls.

### 2.7 Data Requirements
- All money amounts stored as integer minor units (paise) to avoid floating-point currency bugs — never `numeric`/`float` for price fields exposed to payment logic.
- All timestamps stored `timestamptz`, always compared/derived in UTC server-side; display-only conversion happens in the FlutterFlow client.
- Soft-delete is not used for MVP simplicity — categories/items are hard-deleted on vendor request (cascade documented in UX confirm dialogs); orders are **never** deleted, only status-transitioned.

### 2.8 Integration Requirements
- **Supabase Auth** — email/phone auth for Vendor & Customer apps, restricted admin auth for the Admin panel (e.g., invite-only admin accounts, no public signup).
- **Razorpay** — Orders API + Webhooks for payment capture/verification; no client-side "mark as paid" trust.
- **FCM (Firebase Cloud Messaging)** — push delivery triggered from Edge Functions on relevant DB events (new order, status change, approval decision).
- **Supabase Storage** — buckets for `vendor-logos`, `item-images`, with RLS/storage policies mirroring the owning vendor's `owner_id`.
- **Supabase Realtime** — enabled on `orders` (and optionally `vendors.accepting_orders`/`break_until` if live status needs to reflect on the customer app without polling).
- **Supabase Cron** — scheduled job to auto-clear expired `break_until` (flip effective status back to whatever `accepting_orders` says once the break window passes), and any daily maintenance jobs.

## 3. Cross-Cutting Technical Rules (carried from build history)

- **State derivation rule:** any status shown in the UI (store open/closed/break, order status) is read fresh from the DB on load/refresh — never held as a manually-set local variable that could drift from the DB.
- **Modal responsibility separation:** modals/dialogs that collect input (e.g., break duration) return data to the caller; the **caller/parent page** performs the DB write, not the modal itself. Keeps write logic centralized and testable.
- **Component reusability limits:** FlutterFlow components cannot always accept action-type parameters (version-dependent) — reusable visual components (e.g., `QuickActionCard`) stay presentation-only; navigation/action logic is wired at each call site.
