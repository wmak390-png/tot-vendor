# TakeOnTime — Operations Plan

**Version:** 1.0
**Companion to:** `09-Deployment.md`

---

## 1. Monitoring

| Layer | What to monitor | Tool |
|---|---|---|
| Database | Connection count, slow queries, RLS-related errors, disk usage | Supabase Dashboard (Reports), `pg_stat_statements` |
| Edge Functions | Invocation count, error rate, latency per function (`create-order`, `razorpay-webhook`, `update-order-status`, `approve-vendor`, `send-fcm-notification`) | Supabase Dashboard → Edge Functions logs |
| Payments | Webhook delivery success/failure rate, orders stuck in `pending_payment` beyond a threshold (e.g., 15 min) | Razorpay Dashboard + a scheduled query/alert on `orders` |
| Push notifications | FCM delivery success rate | Firebase Console |
| Client apps | Crash-free session rate, app open success | FlutterFlow/Firebase Crashlytics (if wired) |

## 2. Logging

- Every Edge Function logs: request id, caller identity (user id, never full JWT), action attempted, outcome (success/error code) — no PII beyond what's operationally necessary (avoid logging full payment payloads in plaintext long-term; the `payments.raw_webhook_payload` column is the audit record, not application logs).
- Log retention: rely on Supabase's default log retention for the MVP tier; export critical payment-related logs periodically if longer retention is needed for dispute resolution.

## 3. Observability

- A lightweight internal "ops query" set (saved SQL snippets) for the most common questions during MVP operations:
  - Orders stuck in `pending_payment` > 15 minutes.
  - Vendors marked `accepting_orders = true` with zero menu items (mis-onboarded vendor).
  - Vendors on `break_until` for more than 24 hours (likely forgot to end break — candidate for a proactive nudge).
- No dedicated APM/tracing stack for MVP scale — Supabase's built-in logs + these saved queries are sufficient until volume demands more.

## 4. Alerts

| Condition | Alert action |
|---|---|
| `razorpay-webhook` error rate spikes | Immediate — payment integrity risk; page/notify founder-operator directly |
| Any order stuck in `pending_payment` > 15 min | Daily digest at minimum; real-time if volume ever justifies it |
| Edge Function error rate > 5% over 15 min (any function) | Immediate notification |
| Vendor approval queue has items pending > 24h | Daily digest to admin/ops |
| Database approaching plan storage/connection limits | Weekly check during MVP; automate once volume grows |

At MVP scale (small team), these can be simple scheduled queries + email/Slack webhook rather than a full alerting platform — right-sized for the current operational maturity, with room to formalize (e.g., a dedicated alerting tool) as volume grows.

## 5. SLO / SLA

Internal SLOs (not customer-facing contractual SLAs at MVP stage):

| SLO | Target |
|---|---|
| Platform availability | 99.5% monthly (bounded by Supabase's own SLA) |
| Order status propagation latency | < 3s p95 |
| Payment webhook processing | < 5s from Razorpay event to DB update |
| Vendor approval turnaround | < 24h (operational, not automated) |

## 6. Incident Response

1. **Detect** — via an alert (§4) or a user/vendor report.
2. **Triage** — classify severity: **P1** (payments broken / data leak / platform down), **P2** (a core flow degraded, e.g., push not sending but orders still work), **P3** (cosmetic/non-blocking).
3. **Contain** — for P1 payment issues, prefer temporarily disabling new order creation (feature-flag or Edge Function early-return) over a risky hot-fix under pressure.
4. **Fix** — follow the rollback strategy in `09-Deployment.md §8` where applicable; otherwise forward-fix.
5. **Communicate** — notify affected vendors (and customers if payment-related) with a clear, honest status; for RLS/data-leak incidents, this must include what data was exposed and to whom, per standard breach-disclosure practice.
6. **Post-incident** — short written retro: what happened, root cause, what monitoring/test gap allowed it, what's changing (test case added, alert added, etc.) — feed relevant fixes back into `08-Testing-Evaluation.md`.

## 7. Disaster Recovery

- Rely on Supabase's automated Postgres backups (point-in-time recovery, per the project's plan tier) as the primary DR mechanism — no custom backup infra for MVP.
- Before major migrations, take a manual on-demand backup/snapshot as an extra precaution (belt-and-suspenders alongside automated backups).
- Recovery Point Objective (RPO) / Recovery Time Objective (RTO) at MVP stage: bounded by Supabase's own backup frequency/restore process — document the actual numbers from the chosen Supabase plan once selected, rather than assuming a target the plan can't meet.

## 8. Backups

- Database: Supabase automated backups (frequency per plan tier — confirm and record once the production plan is chosen).
- Storage (images): Supabase Storage is itself durable object storage; no separate backup process needed beyond what Supabase provides, but avoid any workflow that deletes-then-recreates images destructively without confirmation (ties back to the UX destructive-confirm rule in `02-UX-Spec.md §4`).
- Configuration/secrets: no "backup" needed beyond the secrets being reproducible from a secure password manager/vault entry — never rely on Supabase dashboard state alone as the only record of a secret's value.

## 9. Cost Monitoring

- Track Supabase usage against plan limits monthly: database size, Edge Function invocations, Storage size/egress, Realtime connections.
- Track Razorpay transaction fees against order volume (cost of payment processing scales with GMV — expected and monitored, not an anomaly).
- Track FCM — free at current expected volume, but monitor if migrating to a paid push-infrastructure tier ever becomes relevant.
- Set a simple monthly cost review as part of ops cadence rather than real-time cost alerting at MVP scale.

## 10. Analytics

- Minimum viable analytics for MVP decision-making (feeds Admin panel's E13 "Platform Monitoring" from `07-Engineering-Plan.md`):
  - Orders per day, GMV per day.
  - Active vendors (`accepting_orders = true` at time of query) vs. total approved vendors.
  - Vendor approval funnel: signups → pending → approved/rejected, and time-in-pending.
  - Order funnel: `pending_payment → confirmed` conversion rate (surfaces checkout drop-off/payment failures).
- No dedicated analytics platform (e.g., Amplitude/Mixpanel) required for MVP — derive from direct SQL against the operational tables; revisit if/when product analytics needs outgrow simple SQL queries.

## 11. Maintenance

- Weekly: review the ops queries in §3, check pending vendor approval queue, check for stuck orders.
- Monthly: review cost (§9), review Edge Function error logs for recurring low-severity issues worth fixing proactively, review and prune stale test/staging data.
- Ongoing: keep `supabase/migrations/` as the single source of truth for schema — any manual dashboard change must be immediately backfilled into a migration file to avoid Staging/Production drift.

## 12. Support

- MVP-stage support channel: direct contact (phone/WhatsApp/email) from vendor/customer to the founder-operator — no ticketing system required yet.
- Common support scenarios to have a documented response for: payment deducted but order not showing (check `payments`/webhook logs first, per §1), vendor stuck in pending approval, item images not uploading (check Storage policy/bucket per `06-API-Data-Design.md`).
- Escalation path: any P1 incident (per §6) automatically becomes the top support priority regardless of what else is queued.
