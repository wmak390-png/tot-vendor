## 1. Data Model Overview

```
users (shared identity — NOT "profiles")
  └─< vendors (owner_id → users.id)
        └─< menu_categories (vendor_id → vendors.id)
              └─< menu_items (category_id → menu_categories.id, vendor_id → vendors.id)
        └─< orders (vendor_id → vendors.id, customer_id → users.id)
              └─< order_items (order_id → orders.id, menu_item_id → menu_items.id)
              └─< payments (order_id → orders.id)  [Razorpay records]
  └─< notifications (user_id → users.id)
```

## 2. Core Table Definitions

> Naming convention: snake_case, plural table names, `id uuid primary key default uuid_generate_v4()`, `created_at`/`updated_at timestamptz default now()` on every mutable table, with the shared `set_updated_at()` trigger attached.

**Derived status (computed, not stored):**
```
effective_status =
  CASE
    WHEN break_until IS NOT NULL AND break_until > now() THEN 'on_break'
    WHEN accepting_orders = true THEN 'open'
    ELSE 'closed'
  END
```

## 3. Order Status State Machine

```
pending_payment → confirmed → accepted → preparing → ready → completed
                                  │
                                  └──────────────→ rejected
pending_payment ──────────────────────────────────→ payment_failed
confirmed/accepted/preparing ─────────────────────→ cancelled  (admin/vendor only, defined reasons)
```

- Every transition is enforced inside the `update-order-status` Edge Function (or a Postgres function called by it) — the client never sends an arbitrary `status` string that gets trusted as-is; the function validates `current_status → requested_status` against the allowed edges above and rejects anything else with `409 Conflict`.
- `pending_payment → confirmed` is **only** triggered by the `razorpay-webhook` function on a verified, signature-checked payment capture event — never by client action.

## 4. Edge Function API Contracts

### 4.1 `POST /functions/v1/create-order`
- **Auth:** required (customer JWT)
- **Body:** `{ vendor_id, items: [{ menu_item_id, quantity }], notes? }`
- **Validation:** vendor must be `is_approved = true` and effective status `open` or `on_break` is rejected (`403`, "vendor not accepting orders"); every `menu_item_id` must belong to `vendor_id` and be `is_available = true`.
- **Success (200):** `{ order_id, razorpay_order_id, amount_paise }`
- **Failure:** `400` (validation), `403` (vendor not orderable), `404` (item/vendor not found), `500` (unexpected)

### 4.2 `POST /functions/v1/razorpay-webhook`
- **Auth:** Razorpay signature header (`X-Razorpay-Signature`), no user JWT
- **Body:** Razorpay's standard webhook payload
- **Validation:** signature must verify against `RAZORPAY_WEBHOOK_SECRET`; idempotent on `razorpay_payment_id` (a repeat delivery of the same event must not double-transition state)
- **Success (200):** `{ received: true }`
- **Failure:** `400` (bad signature) — Razorpay will retry on non-2xx

### 4.3 `POST /functions/v1/update-order-status`
- **Auth:** required (vendor JWT, or admin JWT for `cancelled`)
- **Body:** `{ order_id, new_status }`
- **Validation:** caller must own the vendor tied to the order (or be admin for cancellation); transition must be a legal edge per the state machine
- **Success (200):** `{ order_id, status }` — triggers Realtime broadcast (automatic via Postgres change) + `send-fcm-notification` call
- **Failure:** `403` (not authorized), `409` (illegal transition), `404` (order not found)

### 4.4 `POST /functions/v1/approve-vendor`
- **Auth:** required, admin only
- **Body:** `{ vendor_id, decision: 'approve' | 'reject', reason? }`
- **Validation:** `reason` required when `decision = 'reject'`
- **Success (200):** `{ vendor_id, is_approved }`
- **Failure:** `403` (not admin), `400` (missing reason on reject), `404`

### 4.5 `POST /functions/v1/send-fcm-notification` (internal-only, called by other functions/triggers)
- **Auth:** service-role invocation only, not exposed to clients
- **Body:** `{ user_id, title, body, type, related_id? }`
- **Behavior:** writes a `notifications` row, then calls FCM HTTP v1 API for any registered device tokens for that user; failure to deliver push does not fail the underlying business transaction (best-effort).

## 5. Event Contracts (Realtime)

| Channel | Table/Filter | Consumers |
|---|---|---|
| `orders:vendor_id=eq.<id>` | `orders` INSERT/UPDATE | Vendor app — live order queue |
| `orders:customer_id=eq.<id>` | `orders` UPDATE (status) | Customer app — order tracking |
| `vendors:id=eq.<id>` | `vendors` UPDATE (`accepting_orders`, `break_until`) | Customer app — live status badge (optional, poll-fallback acceptable if deferred) |

## 6. Error Contract (All Edge Functions)

```json
{
  "error": {
    "code": "VENDOR_NOT_ACCEPTING_ORDERS",
    "message": "This vendor is not currently accepting orders.",
    "status": 403
  }
}
```
- `code` is a stable, machine-readable string (UPPER_SNAKE_CASE) the client can switch on for UX (e.g., show a specific banner), never parsed from `message`.
- `message` is safe to show to the end user directly — no stack traces or raw DB errors ever returned to the client.

## 7. Third-Party Integrations Summary

| Integration | Direction | Notes |
|---|---|---|
| Razorpay Orders API | Outbound (Edge Function → Razorpay) | Create order, get checkout params |
| Razorpay Webhooks | Inbound (Razorpay → Edge Function) | Signature-verified, idempotent |
| FCM HTTP v1 | Outbound (Edge Function → FCM) | Best-effort push delivery |
| Supabase Storage | Client ↔ Storage direct (policy-gated) | No Edge Function needed for simple uploads |
