# TakeOnTime — AI Specification (Optional Layer)

**Version:** 1.0
**Status:** Not required for MVP — included for completeness and future extensibility

---

## 1. Applicability

TakeOnTime's MVP is a standard CRUD + payments + realtime-status platform. It has **no core AI-dependent feature** at launch (no chatbot, no recommendation engine, no LLM-generated content in the user-facing product). Per the documentation framework this project follows, this layer is legitimately allowed to "disappear" for MVP — this document exists so that if/when an AI feature is added, it has a defined home and doesn't get bolted on ad hoc.

## 2. Candidate Future AI Features (Not Scoped for Build)

| Candidate | Description | Priority signal |
|---|---|---|
| Menu item description generation | Vendor types a short item name, AI drafts a description + suggested tags. | Nice-to-have, low urgency |
| Smart reorder / "order again" suggestions | Suggest a customer's likely next order based on history + time of day. | Post-MVP growth feature |
| Vendor demand forecasting | Suggest prep quantities based on historical order volume. | Post-MVP, needs order-volume data first |
| Support chatbot (Admin/Customer) | Answer FAQ-style questions (order status, refund policy). | Only if support volume justifies it |
| Fraud/abuse detection on orders | Flag suspicious repeat cancellations or payment patterns. | Security-adjacent, evaluate with real fraud data |

None of these are authorized for build until a separate PRD amendment scopes them.

## 3. If/When AI Is Introduced — Required Sections

Should any candidate above (or a new one) be approved, this document must be filled out **before** implementation begins, covering:

- **Model requirements** — which model/provider, latency/cost budget, on-device vs API.
- **Prompt / system instructions** — versioned prompt templates, stored outside app binaries so they can be updated without a release.
- **Context management** — what data (order history, menu, vendor profile) is passed in, and its size/PII limits.
- **RAG** — if retrieval is needed (e.g., FAQ answering), define the source-of-truth corpus and refresh cadence.
- **Memory** — whether any per-user memory persists across sessions, and its storage/retention policy.
- **Tool calling** — if the AI feature can trigger real actions (e.g., "cancel my order"), define the exact allow-listed tools/functions and confirmation requirements before any state-changing action executes.
- **Agent behavior** — bounded task scope; no open-ended autonomous action on financial or account-state data.
- **Guardrails** — content filtering, refusal behavior for off-topic/abusive input, rate limiting.
- **AI safety** — no AI-generated content should be presented as vendor-verified without a human-in-the-loop review for anything user-facing at first launch of the feature.
- **Evaluation criteria** — accuracy/relevance thresholds and a rollback plan if the feature underperforms.
- **Model fallback** — behavior if the AI provider is unavailable (feature must degrade gracefully, never block core ordering flow).
- **Token/cost limits** — per-request and per-user/day caps, with monitoring hooked into `10-Operations.md`.

## 4. Hard Boundary

Regardless of which AI feature (if any) is eventually approved, it **must never**:
- Alter payment amounts, order status, or vendor approval state autonomously without an explicit user/admin confirmation step.
- Bypass the RLS/Edge Function authorization model described in `03-TRD.md` and `05-Architecture.md` — an AI-triggered action goes through the same authorization path as a human-triggered one.
