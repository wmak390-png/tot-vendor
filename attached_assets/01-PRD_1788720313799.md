# TakeOnTime — Product Requirements Document (PRD)

**Version:** 1.0
**Status:** Living document — updated as each build day/module ships
**Owner:** Founder / Product
**Stack context:** FlutterFlow (3 separate apps) + Supabase (Postgres, Auth, Storage, Realtime, Edge Functions) + FCM + Razorpay

---

## 1. Product Vision

TakeOnTime is a production food-ordering platform that lets local food vendors (canteens, small restaurants, cloud kitchens) manage their menu and orders, and lets customers browse nearby vendors, order ahead, pay online, and pick up or receive their food **on time** — without the vendor being overwhelmed by walk-in + app-order chaos.

The name "TakeOnTime" encodes the core promise: orders are placed ahead, paid for upfront, and ready at a promised time — reducing wait-time friction for the customer and order-floor chaos for the vendor.

## 2. Problem Statement

- Small food vendors have no lightweight, affordable way to accept pre-orders and manage a live menu.
- Customers waste time waiting in line for food that could have been prepared in advance.
- Existing platforms (Swiggy/Zomato-class) are heavy, expensive, delivery-first, and take large commissions — TakeOnTime targets **order-ahead + pickup / prepaid**, not last-mile delivery logistics, at least for MVP.
- Vendors need a simple way to pause orders (temporary break) without going fully offline, and to manage stock/menu without technical help.

## 3. Target Users

| User | Description |
|---|---|
| **Vendor** | Owner/staff of a food business (canteen, restaurant, cafe, cloud kitchen) who manages menu, accepts/rejects orders, and controls store availability. |
| **Customer** | End user who discovers vendors, browses menu, places prepaid orders, and tracks order status. |
| **Admin** | Internal TakeOnTime staff who approve/reject vendor onboarding, monitor platform health, handle disputes, and manage platform-level configuration. |

This is explicitly **not** a single role-based app — Vendor, Customer, and Admin are **three separate applications** (two FlutterFlow mobile apps + one FlutterFlow web admin panel), all sharing one Supabase backend.

## 5. User Journeys (Core)

### Vendor journey
1. Sign up → submit business details → status `pending_approval`.
2. Admin approves → vendor gains access to dashboard.
3. Vendor builds menu (categories → items).
4. Vendor toggles "Accepting Orders" on, sets store live.
5. Order arrives (realtime) → vendor accepts/rejects → updates status through prep → ready.
6. Vendor can pause orders temporarily ("Temporary Break") without fully closing the store profile.

### Customer journey
1. Sign up / login.
2. Browse nearby/available vendors (only vendors with `is_approved = true` and `accepting_orders = true` are orderable; others shown as closed).
3. View vendor menu (categories → items), add to cart.
4. Checkout → Razorpay prepayment (COD explicitly out of scope for MVP).
5. Track order status in realtime.
6. Receive push notification (FCM) at each status change.
7. Pick up / receive order.

### Admin journey
1. Login to web admin panel.
2. View pending vendor approvals → approve/reject with reason.
3. Monitor live order volume, vendor status, disputes.
4. Manage platform-level settings (categories taxonomy, commission if applicable, banned vendors/users).

## 6. Feature Set (MVP Scope)

### Vendor App
- Auth (Supabase Auth, email/phone)
- Vendor onboarding form → `pending_approval` state
- Store dashboard (Store tab): business header, Accepting Orders toggle, Temporary Break control, Quick Actions grid
- Menu management: Categories (CRUD) → Items (CRUD), sold-out toggle, item images (Supabase Storage)
- Order management: live order queue (Realtime), accept/reject, status progression
- Push notifications (FCM) for new orders
- Profile / business settings

### Customer App
- Auth (Supabase Auth)
- Vendor discovery (list/search, status-aware: open/closed/on-break)
- Vendor menu browse (categories → items)
- Cart + checkout
- Razorpay prepaid payment (**no COD**)
- Order tracking (Realtime status updates)
- Push notifications (FCM) for order status
- Order history

### Admin Web Panel
- Admin auth (restricted)
- Vendor approval queue (approve/reject with reason, view submitted docs)
- Vendor list / search / suspend
- Order monitoring dashboard
- Platform configuration (category taxonomy, support contact, etc.)
- Basic analytics (orders/day, active vendors, GMV)

## 7. Explicitly Out of Scope for MVP

- Cash on Delivery / Cash on Pickup (**COD is skipped — prepaid only**)
- Delivery logistics / rider assignment (pickup-first model)
- Role-based single app (deliberately three separate apps instead)
- Loyalty programs, coupons/promo codes (flagged as future "Quick Action" placeholder only)
- Advanced analytics/reporting beyond basic counts
- Multi-language support
- In-app chat between vendor and customer

## 8. Functional Requirements (Summary)

See **TRD** (`03-TRD.md`) for the full technical breakdown. At product level:

- FR-1: A user record must exist in a single shared `users` table (not `profiles`) regardless of which app they signed up through, with a `role` or app-context distinguishing vendor/customer/admin association.
- FR-2: A vendor is not orderable by customers until `is_approved = true` by an admin.
- FR-3: Vendors can independently control `accepting_orders` (persistent on/off) and a `temporary_break` (time-boxed pause) — these are distinct states.
- FR-4: All payments must go through Razorpay before an order is confirmed; no order can exist in a "confirmed" state without a successful payment record.
- FR-5: Order status changes must propagate to the customer app in near-real-time via Supabase Realtime, and trigger an FCM push.
- FR-6: All vendor-owned data (categories, items, orders) must be protected by Postgres RLS scoped to the vendor's `owner_id = auth.uid()`.

## 9. Business Requirements

- Must run on Supabase free/pro tier economics during MVP phase (cost-conscious architecture).
- Must be buildable incrementally, day-by-day, by a solo/small technical team using FlutterFlow no-code + light Edge Function code.
- Must be extensible to add delivery, COD, promotions, and loyalty post-MVP without a schema rewrite (additive migrations only).

## 10. Success Metrics

| Metric | MVP Target |
|---|---|
| Vendor onboarding → first live menu | < 1 day per vendor |
| Order placement → payment success rate | > 95% |
| Order status update latency (vendor action → customer sees it) | < 3 seconds (Realtime) |
| Push notification delivery rate | > 90% |
| Vendor approval turnaround (admin) | < 24 hours |
| Crash-free session rate (both apps) | > 99% |

## 11. Constraints

- Solo/small dev team, no-code-first (FlutterFlow) with Supabase Edge Functions for logic that can't live in RLS/client.
- One-day-at-a-time build cadence — every module must be independently shippable and testable before the next begins.
- Prepaid-only at launch (Razorpay) — no cash handling flows to design for.
- Three independent app codebases sharing one backend — requires strict API/RLS contracts since there is no shared client-side auth/role logic to lean on.
