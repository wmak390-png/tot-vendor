## 1. Design System Reference

All visual tokens (color, type, spacing, radius, icon style) live in a single **`Design.md`** so individual page specs never repeat them. Summary (source of truth = `Design.md`):

- Platform: FlutterFlow, Material Design 3, screen baseline 390×844
- Primary: `#FF6B00` / `#FF6B35` (confirm one canonical value in Design.md)
- Background: `#F8F9FA`
- Text: `#1F2937` / Secondary `#6B7280`
- Success: `#16A34A` · Error: `#DC2626`
- Font: Poppins · Icons: Material Symbols Rounded
- Grid: 8pt · Card radius: 16 · Page padding: 16

Page-level specs (see `Category List Page`, `Items List Page`, `Store Page`, etc.) intentionally omit these and reference `Design.md` only.

## 3. User Flows

### 3.1 Vendor — Store Availability Flow
1. Vendor opens **Store tab** → sees current status derived entirely from DB (never manually assigned client-side).
2. Toggling **Accepting Orders** → direct DB update → UI refreshes from the write, not an optimistic local flag.
3. Tapping **Temporary Break** → modal collects a duration only (30/60/120 min or "End Break") → modal returns the duration to the parent page → **parent** performs the DB write (`break_until = now() + duration`) → **timer display is read-only**, computed from `break_until`, never stored as a running countdown state.
4. Status badge precedence: **On Break** (red) > **Closed** (`accepting_orders = false`, grey) > **Open** (green).

### 3.2 Vendor — Menu Management Flow
1. Menu tab → Category List Page (flat list, sortable by `sort_order`).
2. Tap **+** → Category Form Dialog (Create) → name + sort order → insert → list refreshes.
3. Tap category row → Items List Page, scoped via passed params (`selectedCategoryId`, `selectedCategoryName`).
4. Items List Page → search + status filter (All/Active/Sold Out) → tap **+** or item card → Item Form Page (create/edit) with image upload to Supabase Storage.
5. Delete category → confirmation modal warns that child items cascade-delete.
6. Delete item → confirmation modal, item-only, category untouched.

### 3.3 Customer — Order Flow
1. Discover vendors (only `is_approved = true`; status badge shows Open/Closed/On Break, closed vendors browsable but not orderable).
2. Browse categories → items → add to cart (single-vendor cart).
3. Checkout → review → Razorpay payment sheet.
4. On payment success (verified server-side via Edge Function webhook, never trusted from client) → order created in `confirmed` state.
5. Realtime subscription on the order row → status pill updates live (`confirmed → accepted → preparing → ready → completed`), each transition also fires an FCM push.

### 3.4 Admin — Approval Flow
1. Admin sees pending vendor queue, sorted oldest-first.
2. Opens vendor detail → reviews submitted info/docs.
3. Approve → `is_approved = true`, vendor notified (FCM/email) → vendor app's `PendingApprovalPage` router redirects to `MainNavPage` on next load.
4. Reject → reason required → vendor sees `AccountIssuePage` with the reason.

## 4. Page-Level UX Behaviors (Applies Platform-Wide)

Every list/detail page in all three apps must define these five states explicitly — no page ships without all five:

| State | Rule |
|---|---|
| **Loading** | Skeleton cards matching the real card shape — never a blank screen or bare spinner for list pages. |
| **Empty** | Icon/illustration + short title + subtitle + a primary action button where applicable (e.g., "Add Category"). |
| **Error** | `error_outline` icon + short title + **Retry** button that re-runs the same query. |
| **Success (populated)** | Standard list/grid render. |
| **Destructive-confirm** | Any delete requires a confirmation dialog naming the entity and the consequence (e.g., cascading deletes) before the destructive action runs. |

## 6. Navigation Rules

- Tab-to-tab navigation within `MainNavPage` (e.g., Store's "Today's Orders" quick action → Orders tab) must switch the existing `PageView`/tab index in place — **never** push a new page stack on top of the nav shell.
- Drill-down navigation (Category → Items → Item Form) **does** push a new page and shows a back button; bottom navigation is hidden on these detail pages (per Items List Page spec) since they are not top-level tabs.
- All cross-page parameters are explicit FlutterFlow page parameters (`selectedCategoryId`, `selectedCategoryName`, `itemId`, etc.) — never relied upon via global/app state for page-scoped data.

## 7. Accessibility

- Minimum tap target 44×44 logical px for all icon buttons (edit/delete/chevron).
- Color is never the only status indicator — status chips always carry text ("Active"/"Sold Out", "Open"/"Closed"/"On Break") alongside color.
- Sufficient contrast: body text `#1F2937` on `#F8F9FA`/white passes WCAG AA at the specified sizes.
- All images (item photos, business logo) require alt/semantic labels for screen readers where FlutterFlow supports it.

## 8. Responsive Behavior

- Baseline design at 390×844; all layouts must use Auto Layout / flexible constraints (no hardcoded widths) so they degrade gracefully on larger phones and small tablets.
- Admin web panel is desktop-first (wide table/list layouts) but must remain usable down to a tablet breakpoint.

## 9. Dark Mode

- Deferred for MVP on Vendor/Customer apps but component structure (semantic color tokens, not hardcoded hex inline per-widget) should not block adding it later — call out in `Design.md` as a token-based system precisely so dark mode is a token swap, not a rebuild.
