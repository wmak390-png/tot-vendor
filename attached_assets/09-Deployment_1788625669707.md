# TakeOnTime — Deployment Plan

**Version:** 1.0
**Companion to:** `05-Architecture.md`, `07-Engineering-Plan.md`

---

## 1. Environments

| Environment | Supabase project | Purpose |
|---|---|---|
| **Local/Dev** | Local Supabase (CLI) or a dedicated `takeontime-dev` project | Day-to-day building of each module, throwaway data |
| **Staging** | `takeontime-staging` Supabase project | Integration testing, UAT, Razorpay **test mode**, FCM to test devices only |
| **Production** | `takeontime-prod` Supabase project | Live vendors/customers, Razorpay **live mode**, FCM to real devices |

Three separate Supabase projects (not one project with environment-flag rows) — cleanest isolation for RLS testing and avoids any risk of test data touching production, especially important since money/payments are involved.

## 2. CI/CD

- **Database migrations:** all SQL (tables, RLS, functions, triggers) tracked as versioned files under `supabase/migrations/` in Git, applied via `supabase db push` — never hand-edited directly in the Staging/Prod dashboards without a matching migration file committed first.
- **Edge Functions:** tracked under `supabase/functions/<name>/`, deployed via `supabase functions deploy <name> --project-ref <ref>`; each function has its own directory and `deno.json` where needed.
- **FlutterFlow apps:** FlutterFlow's own Git sync (or manual export) pushed to per-app GitHub repos (`takeontime-vendor-app`, `takeontime-customer-app`, `takeontime-admin-panel`); no custom CI pipeline required for the FlutterFlow layer itself beyond what FlutterFlow's build/export provides, but app-store submission (Vendor/Customer apps) and web hosting (Admin panel) are still tracked as explicit release steps below.
- **Recommended minimal automation:** a GitHub Action that lints/validates SQL migration files and runs the Edge Function unit tests (§`08-Testing-Evaluation.md §2`) on every PR touching `supabase/`.

## 3. Infrastructure

- Supabase-managed Postgres, Auth, Storage, Realtime, Edge Functions, Cron — no self-hosted infra for MVP.
- Firebase project for FCM (separate from Supabase, standard Google Cloud project).
- Razorpay account with separate **test** and **live** API key pairs, mapped 1:1 to Staging/Production environments respectively — test keys must never be present in the Production Edge Function secrets, and vice versa.

## 4. Deployment Strategy

- **Database:** migrations applied Staging first, verified via the RLS/integration test suite (`08-Testing-Evaluation.md`), then applied to Production during a low-traffic window (early MVP has no real "peak," so this is precautionary discipline, not a hard requirement).
- **Edge Functions:** deploy to Staging, run the E2E order flow (`08-Testing-Evaluation.md §4`) end-to-end against Staging with Razorpay test mode before promoting the same function code to Production.
- **FlutterFlow apps:** test builds distributed via FlutterFlow's test/preview link or TestFlight (iOS)/internal testing track (Android) before any public app-store release; Admin web panel deployed to a staging subdomain before promoting to the production domain.
- No blue/green or canary infra at MVP scale — a single Production environment per app, with Staging as the pre-release gate.

## 5. Configuration & Secrets

| Secret | Where it lives | Never appears in |
|---|---|---|
| Supabase service role key | Edge Function environment variables (`supabase secrets set`) | Any client app, any Git-committed file |
| Razorpay key secret + webhook secret | Edge Function environment variables, per environment | Client apps (only the **public** Razorpay key ID is client-side) |
| FCM server key / service account | Edge Function environment variables | Client apps |
| Supabase anon key + project URL | Client app config (this is expected/safe — anon key relies on RLS, not secrecy) | N/A — safe to be public |

- All secrets managed via `supabase secrets set` per project (Staging vs Production have independent secret values) — never hardcoded in Edge Function source.
- `.env`/secret files excluded via `.gitignore`; only `.env.example` (with placeholder values) is committed.

## 6. Database Migrations

- One migration file per logical change (e.g., `0001_users_table.sql`, `0002_vendors_table.sql`, `0003_menu_categories.sql` ...), matching the day-by-day build history already established.
- Every migration that adds a table **includes its RLS policies in the same file** — a table is never committed "RLS-enabled later," per the security requirement in `03-TRD.md §2.5`.
- Rollback: since hard-deletes aren't the norm for business data (orders are append/status-only per `06-API-Data-Design.md`), rollback strategy is primarily **forward-fix migrations** rather than down-migrations; down-migrations are still written for schema-only changes (new tables/columns) where feasible.

## 7. Release Process

1. Feature/day's work completed and passes its own testing checklist (established pattern).
2. Merge to `main` in the relevant Git repo (Supabase repo, or the specific FlutterFlow app repo).
3. Deploy migrations/functions to Staging.
4. Run relevant integration/E2E checks from `08-Testing-Evaluation.md`.
5. Deploy to Production (migrations/functions), then promote/release the corresponding FlutterFlow app build.
6. Smoke-test the specific changed flow directly in Production immediately after release.
7. Tag the release (see versioning below).

## 8. Rollback Strategy

- **Edge Functions:** redeploy the previous known-good version (`supabase functions deploy` from the prior Git tag) — fast rollback since functions are stateless.
- **Database:** prefer a forward-fix migration; only attempt a destructive rollback migration if the faulty migration has not yet accumulated production data that depends on it.
- **FlutterFlow apps:** revert to the previous store build (iOS/Android use phased rollout; halt and revert if a release shows elevated crash rate per `10-Operations.md` monitoring); Admin web panel rollback is a redeploy of the previous build artifact.

## 9. Versioning

- Supabase schema/functions: Git tags per release, e.g., `db-v0.4.0`, `fn-v0.4.0`.
- Vendor app / Customer app / Admin panel: independent semantic versions per app (e.g., `vendor-app-v0.3.0`), since they release on independent cadences per `05-Architecture.md` ADR-001.
- Every tag's changelog references which Engineering Plan epics/stories (`07-Engineering-Plan.md`) it closes, for traceability back to the PRD.
