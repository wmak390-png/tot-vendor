## PROJECT-LEVEL RULES (non-negotiable, apply to every response)

1. **Three separate apps, not role-based auth.** Vendor app, Customer app, and Admin web panel are independent FlutterFlow projects sharing one Supabase backend. Never suggest merging them.
2. **Build order:** Vendor app fully complete → Customer app fully complete → Admin panel. Do not start a later app's epics before the earlier app's are done, unless I explicitly say otherwise.
3. **Identity table is `users`**, never `profiles`.
4. **Prepaid only — no COD.** Never introduce a cash-on-delivery/pickup flow unless I explicitly ask to add it later.
5. **State is always derived from the DB**, never held as a manually-set client flag that could drift. Anything shown as a "status" (store open/closed/break, order status) is read fresh on load or via Realtime — never assumed.
6. **Modals/dialogs return data to the caller; the parent page performs the DB write.** Never put a database write inside a modal itself.
7. **Reusable FlutterFlow components stay presentation-only** where FlutterFlow can't pass actions as parameters — navigation/onTap logic is wired at the call site, not inside the component.
8. **RLS is written in the same migration as the table**, never added later. Every vendor-scoped table's RLS resolves through: `auth.uid() → users.id → vendors.owner_id → vendors.id → child.vendor_id`.
9. **All money is stored as integer paise (minor units), never float.**
10. **No client-side trust for payments or order status.** Order state transitions and payment confirmation happen only inside Edge Functions (`create-order`, `razorpay-webhook`, `update-order-status`), never via a direct client table write.
